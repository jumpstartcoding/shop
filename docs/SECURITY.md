# Security

How the app protects customer records, documents, and payments, what was checked against spec §52, and what the shop owner should do to keep it that way. Last reviewed October 2026.

## Owner checklist

Before customers use the site:
- [ ] The owner login has a long, unique password (12+ characters; a password manager helps).
- [ ] The go-live checks on the latest Deploy run show no ❌ (Actions → Deploy → newest run → Summary).
- [ ] The demo login does not exist in production (the go-live checks fail if it does).
- [ ] `ORIGIN_SECRET` is a random 64-character value (`openssl rand -hex 32`), stored only in GitHub secrets.
- [ ] AWS root account has MFA turned on and isn't used day to day.
- [ ] The GitHub account that owns the repo has two-factor sign-in. Anyone who can push to `main` can deploy.
- [ ] Alert and budget emails are confirmed (the subscription emails AWS sends after the first deploy).
- [ ] A backup has run, and a restore has been practiced once (docs/BACKUPS.md).
- [ ] Authorization, terms, and warranty wording in Settings has been reviewed for your state. The app records signatures; it doesn't decide what they legally mean.

Ongoing:
- [ ] Sign out on shared computers. Sessions last up to 30 days on a device.
- [ ] Look at alert emails when they arrive; they mean the app logged an error.
- [ ] Rotate the Stripe keys and the database password if anyone who had them leaves (see "Rotating secrets" in DEPLOYMENT.md).

## Spec §52 review

| Risk | How it's handled | Checked by |
|---|---|---|
| **SQL injection** | All queries go through SQLAlchemy with bound parameters. The few raw `text()` statements are constant strings (health check, numbering counter, index definitions); none is built from input. | Code review (`grep` for `text(`); every endpoint is exercised by tests on real Postgres. |
| **XSS** | React escapes everything it renders; the code has no `dangerouslySetInnerHTML`, `eval`, or inline scripts. PDF templates use Jinja autoescaping. The production site sends a strict Content-Security-Policy (scripts only from the site itself, no plugins, no framing). | Built site browsed under the production CSP at phone size (public pages, admin, signing page): zero violations. |
| **CSRF** | Session cookie is `SameSite=Strict`, plus a double-submit token (`X-CSRF-Token` header must match the `shop_csrf` cookie, compared in constant time) on every state-changing admin request. | `test_state_changes_need_csrf_on_every_private_route` walks every POST/PATCH/PUT/DELETE route. |
| **Broken authorization / IDOR** | One shop per deployment, so there are no other tenants' records to reach. Every admin route depends on `require_user`; roles go through one `require_role` dependency for when employees are added. Customers never get IDs to guess: they get 256-bit, purpose-scoped, expiring, revocable links whose hashes are stored. | `test_every_private_route_requires_sign_in` calls every non-public route signed out (all return 401). `test_public_routes_are_the_expected_ones` fails if a new public route appears unreviewed. |
| **Customer data leakage** | Customer-facing pages and PDFs are built from separate snapshot functions that never include internal notes, part cost, or markup. | `test_customer_link_page_never_carries_internal_fields` (page and PDF). |
| **Insecure file uploads** | Uploads are limited to the logo and signatures. Both are size-limited, decoded with Pillow, and re-encoded to a fresh PNG (dropping anything hidden in the original). Storage keys are generated by the server, never taken from input. Files sit in a private, encrypted, versioned S3 bucket that's only reachable through the app. | `test_signature_rules`, `test_logo_upload`. |
| **Exposed secrets** | Secrets live in SSM Parameter Store (encrypted) and GitHub encrypted secrets, never in the repo or the website bundle. The deploy step refuses to upload a website build containing anything shaped like a Stripe or AWS key. GitHub signs in to AWS with short-lived OIDC tokens limited to the `main` branch, so there are no long-lived AWS keys to leak. | `.env` is git-ignored; deploy workflow bundle scan. |
| **Payment security** | Card entry happens only on Stripe's hosted Checkout; card data never reaches this app. Payments are recorded only from webhooks with a verified signature (5-minute replay window), exactly once per event, inside a locked transaction. | 28 tests in `test_payments.py` (forged, tampered, replayed, duplicate, concurrent, and partial-failure webhooks). |
| **Brute force** | 10 failed logins lock the account for 15 minutes. Public forms (booking, contact, questions) are limited per visitor IP per hour, with a honeypot field. | `test_lockout_after_repeated_failures`, `test_booking_honeypot_and_rate_limit`. |
| **Spoofed visitor IP** | *Found and fixed in this review:* the app used to trust the first `X-Forwarded-For` entry, which visitors can set themselves, so rate limits could be dodged and signature records could carry a fake IP. Now a CloudFront Function writes `X-Viewer-Ip` from the real connection (overwriting anything sent), and the app trusts that header only on requests carrying CloudFront's origin secret. | `test_client_ip_never_trusts_x_forwarded_for`, `test_spoofed_forwarded_for_cannot_dodge_the_booking_limit`. |
| **Direct access around CloudFront** | The Lambda Function URL is public by necessity (Stripe must reach the webhook), but the app refuses any request without the secret header CloudFront adds. | `test_origin_secret_blocks_direct_access`; CI smoke test of the built image. |
| **Transport** | HTTPS only: CloudFront redirects HTTP, TLS 1.2+, HSTS for two years; S3 buckets deny non-TLS requests; Neon requires TLS. | `infra/template.yaml`. |
| **Vulnerable dependencies** | Few dependencies, all pinned in lock files. | `npm audit` and `pip-audit` on October 15, 2026: no known vulnerabilities. ECR scans each image on push. |

## Data the app stores

- **Customers and vehicles:** names, phone, email, address, vehicle details, notes.
- **Signatures:** signer name, contact, drawn-signature image or typed name, time, IP address, browser user agent, the exact document version signed, and its SHA-256.
- **Payments:** amount, method, Stripe payment and session IDs. No card numbers, CVCs, or bank details, ever.
- **Logins:** email, Argon2id password hash, hashed session tokens.

Not stored: full card data, Social Security numbers, driver's license numbers.

## Known limits (V1)

- **One login, no two-factor.** The app has one owner account. Two-factor sign-in and employee accounts are on the roadmap.
- **No web application firewall.** AWS WAF costs at least $5–8/month, more than the whole rest of the stack. App-level limits (login lockout, per-IP form limits) and Lambda's built-in scaling cover a one-shop site. Add WAF if abuse ever shows up.
- **The origin secret is visible to AWS admins** in the Lambda console's environment variables. It only stops direct calls to the Function URL; it doesn't unlock any data.
- **The repository is public.** It contains no secrets, but anyone can read the code. Making it private changes nothing in the deploy setup.
- **Concurrency cap is off by default.** New AWS accounts often can't reserve concurrency. Once yours can, set `RESERVED_CONCURRENCY` (e.g. 10) to bound cost and database connections under a traffic flood.

## Reporting a problem

If you find a security issue, email the shop owner directly rather than opening a public GitHub issue.
